# Playwright workshop

Інструкція для початківців: як записати сценарій, перетворити запис на тест і запускати його.

Застосунок уже працює на [https://victorycenter.online/login](https://victorycenter.online/login). Адреса береться з `.env` (`BASE_URL`), інакше з конфігу: `https://victorycenter.online`. Цей репозиторій сам сервер не піднімає.

## Перед першим запуском

```powershell
npm install
npx playwright install
```

У `.env` у корені проєкту мають бути:

```
BASE_URL=https://victorycenter.online
ADMIN_EMAIL=...
ADMIN_PASSWORD=...
```

Паролі в тести не вписуйте. Готовий тест читає їх через `process.env`.

## Де що лежить

| Шлях | Що це |
|---|---|
| `tests/records/` | Сирий запис з codegen. Це чернетка, не готовий тест. |
| `tests/*.spec.ts` | Тести, якими вже можна користуватися. |
| `tests/helpers/` | Спільні дії (вхід, підготовка даних). |
| `docs/` | Розбір запису і текст тест-кейсів. |
| `playwright.config.ts` | Адреса, браузери, пауза між діями, ретраї. |

Приклад пари «запис → тест»: `tests/records/pc-1.spec.ts` і `tests/pc-01-admin-team-page.spec.ts`. Розбір цього запису лежить у `docs/pc-1-recording-analysis.md`.

## Як записати тест

1. Відкрийте застосунок у браузері і пройдіть сценарій руками один раз, щоб знати маршрут.
2. Запустіть запис. Файл кладіть у `tests/records/`, не поруч із готовими тестами:

```powershell
npx playwright codegen https://victorycenter.online/login --output=tests/records/my-scenario.spec.ts --target=playwright-test
```

3. У вікні браузера виконайте лише ті кроки, які входять у цей кейс. Зайве (відкрили не ту сторінку, клікнули двічі) теж потрапить у файл.
4. Зупиніть запис. Playwright збереже файл сам.

Запис фіксує те, що ви зробили, а не те, що має перевіряти тест. Назва тесту буде `'test'`, адреси будуть повні, у файлі з’являться кліки перед уведенням тексту, натискання Tab і повторні кліки.

## Як читати запис

Відкрийте файл і для кожного рядка дайте відповідь на три питання:

- Це дія користувача чи випадковий рух (клік у поле перед `fill`, Tab, другий і третій клік по тій самій кнопці)?
- Що доводить `expect` поруч? Перевірка після кліку по тій самій кнопці часто не доводить нічого нового.
- Локатор лишиться одним елементом, коли на сторінці з’явиться модалка або ще одне поле з подібною назвою?

Типові знахідки в записі:

- `page.goto('https://victorycenter.online/login')` замість `page.goto('/login')`. Базова адреса вже задана в конфігу.
- Логін і пароль прямо в коді.
- `getByRole('heading')` без імені. Другий заголовок на сторінці зламає тест.
- `locator('#root')`. Це контейнер фреймворку, а не елемент, який бачить людина.
- Ручний `goto` на наступну сторінку замість очікування переходу після кнопки.
- Немає перевірки того, заради чого існує кейс: куди потрапили, що відкрилося, що збереглося.

## Як полагодити запис

Готовий тест створюйте новим файлом `tests/<feature>.spec.ts`. Запис у `tests/records/` залиште як є, поки розбір не закінчено.

1. Поруч тримайте текст кейса (для цього набору це `docs/TM-01-create-team-member.md`). Запис часто захоплює сусідні кроки, які в цей тест не входять.
2. Залиште одну поведінку користувача. Назва тесту каже, що зробили і що має статися.
3. Приберіть артефакти рекордера: клік перед `fill`, Tab, повторні кліки.
4. Адреси зробіть відносними: `page.goto('/login')`.
5. Облікові дані візьміть з `.env`.
6. Звузьте локатори: `getByRole('button', { name: 'Увійти', exact: true })`. Якщо на сторінці два однакові елементи, обмежте область (`getByRole('navigation')`, контейнер модалки), а не беріть `.first()`.
7. `expect` має доводити результат. Після входу це адреса, видимий текст і елемент, який є лише в цього користувача. Після відкриття сторінки це її адреса і елемент, якого немає на інших сторінках.
8. Те, що не є предметом тесту (уже створена категорія, вже виконаний вхід для наступних кейсів), готуйте через `tests/helpers/`, а не довгим кліканням по інтерфейсу.
9. Запустіть полагоджений тест однією командою з розділу нижче і подивіться, що він перевіряє насправді.

Коротко, чим відрізняється готовий тест від запису `pc-1`:

- відносний `/login` і облікові дані з `.env`;
- один клік «Увійти», далі очікування відповіді `/api/auth/login` і переходу на `/admin-panel`;
- посилання «Команда» шукається в навігації, після кліку перевіряються адреса `/admin-panel/team` і кнопка «Додати в команду».

## Як досліджувати промптами

Просіть спочатку розбір, і лише наступним повідомленням — правку файлу. Інакше легко отримати тест, який проходить, але перевіряє не те.

Вставляйте шлях до запису, шлях до кейса і текст помилки. Без цього відповідь буде загальною.

**Розібрати запис, код не чіпати**

```text
Розібери tests/records/pc-1.spec.ts проти PC-1 і PC-2 у docs/TM-01-create-team-member.md.
По кожному рядку напиши: що це за дія, що доводить перевірка поруч, що зайве, чим небезпечний локатор.
Наприкінці — список того, чого бракує, щоб падіння мало зрозумілу причину.
Файли не змінюй.
```

**Звірити локатори з живою сторінкою**

```text
Застосунок відкритий на https://victorycenter.online/login. Пройди шлях із tests/records/pc-1.spec.ts і для кожного локатора порахуй, скільки елементів він знаходить до відкриття модалки і після.
Запропонуй локатор, який лишається одним елементом. Не використовуй .first(), .nth() і force: true.
```

**Полагодити запис**

```text
Перенеси сценарій PC-1 із tests/records/pc-1.spec.ts у tests/pc-01-admin-team-page.spec.ts.
Один тест — одна поведінка. Назва описує дію і очікуваний результат.
Прибери кліки перед fill, Tab, повторні кліки і повні URL. Логін і пароль візьми з .env.
expect лиши в тесті. Він має доводити результат кроку, а не факт кліку.
```

**Зрозуміти падіння**

```text
Упав tests/pc-01-admin-team-page.spec.ts. Ось помилка:

<вставте текст помилки з термінала>

Поясни, на якому кроці це сталося і яка найменша правка це закриває.
Не додавай waitForTimeout, networkidle і обхід strict mode.
```

**Перевірити, що тест доводить кейс**

```text
Порівняй tests/pc-01-admin-team-page.spec.ts з PC-1 у docs/TM-01-create-team-member.md.
Напиши, яку умову кейса тест доводить, а яку ні. Код не змінюй, поки я не попрошу.
```

Якщо відповідь пропонує зачекати фіксовану кількість мілісекунд або взяти перший зі знайдених елементів, попросіть інший варіант: дочекатися відповіді мережі, адреси або видимого елемента.

## Запуск тестів

Усі команди виконуйте з кореня репозиторію.

Конфіг уже відкриває браузер (`headless: false`) і ставить паузу 500 мс між діями (`slowMo`). Тест, що впав, повторюється ще двічі (`retries: 2`). Проєктів три: Chromium, Firefox і WebKit, тож без `--project` кожен тест іде тричі. Для розбору достатньо Chromium.

### Усі тести

```powershell
npx playwright test --project=chromium
```

Повний прогін у трьох браузерах:

```powershell
npx playwright test
```

Подивитися, що буде запущено, без самого запуску:

```powershell
npx playwright test --list --project=chromium
```

### Один тест

За шляхом до файлу:

```powershell
npx playwright test tests/pc-01-admin-team-page.spec.ts --project=chromium
```

За частиною назви:

```powershell
npx playwright test --project=chromium -g "admin logs in"
```

Лише тест, що починається на вказаному рядку:

```powershell
npx playwright test tests/pc-01-admin-team-page.spec.ts:10 --project=chromium
```

### Один тест уповільнено

Пауза між діями вже є в кожному запуску: `slowMo: 500` у `playwright.config.ts`. Команда одного тесту вище показує браузер із цією паузою.

У `npx playwright test` цієї версії немає прапорця `--slow-mo`. Щоб розібрати один тест ще повільніше, відкрийте його в інспекторі. Виконання зупиняється перед кожним кроком, далі кроки йдуть кнопкою Resume:

```powershell
npx playwright test tests/pc-01-admin-team-page.spec.ts --project=chromium --debug
```

Щоб подовжити саме паузу між діями, на час перегляду змініть `slowMo` у `playwright.config.ts` (наприклад, на `1500`) і після перегляду поверніть `500`.

### Один тест із більшим часом виконання

Звичайний ліміт тесту — 30 секунд. Для повільного сценарію підніміть його лише на цей запуск, у мілісекундах:

```powershell
npx playwright test tests/pc-01-admin-team-page.spec.ts --project=chromium --timeout=120000
```

`--timeout=0` знімає ліміт зовсім. Так зручно дивитися довгий сценарій, але для звичайного прогону ліміт краще лишати.

Це час на весь тест. Кожен `expect` окремо чекає до 5 секунд. Якщо перевірка не встигає, а тест ще в межах свого ліміту, таймаут задають на самій перевірці: `await expect(locator).toBeVisible({ timeout: 15_000 })`. Краще дочекатися конкретної відповіді сервера, як у `tests/pc-01-admin-team-page.spec.ts`, ніж збільшувати всі очікування.

Поки шукаєте причину падіння, вимкніть повтори, інакше той самий тест пройде до трьох разів:

```powershell
npx playwright test tests/pc-01-admin-team-page.spec.ts --project=chromium --timeout=120000 --retries=0
```

## Коли тест упав

Після прогону відкрийте HTML-звіт:

```powershell
npx playwright show-report
```

Там є текст помилки, скріншот падіння і trace з повтору. Trace показує кожну дію, знімок сторінки і мережеві запити. Для розбору промптом скопіюйте текст помилки в запит із розділу вище.

Повторний прогін лише тих тестів, що впали минулого разу:

```powershell
npx playwright test --last-failed --project=chromium --retries=0
```
